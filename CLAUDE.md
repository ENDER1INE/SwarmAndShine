# CLAUDE.md — Инструкции для работы над проектом

Этот файл — обязательный контекст для ИИ при любой работе с кодом в этом репозитории. Проект — портфолио-пис (survivors-like по формуле Brotato, полный дизайн в [`Documentation~/GDD_Survivors_Like.docx`](Documentation~/GDD_Survivors_Like.docx)), поэтому приоритет architecture quality выше приоритета скорости написания кода. Код будут смотреть на собеседованиях — чистота важнее количества фич.

---

## 1. Контекст проекта

- Жанр: 2D top-down survivors-like, ориентир — Brotato (волны → магазин → волны, лимит 6 слотов оружия, статы через StatModifier).
- Движок: Unity, 2D, mobile (Android).
- Полный дизайн — в GDD (`Documentation~/GDD_Survivors_Like.docx`). Перед реализацией любой игровой системы (оружие, волны, магазин, мета-прогрессия) свериться с соответствующим разделом ГДД, а не изобретать механику заново.
- Референс по арту и визуальному стилю — `Documentation~/Art_Asset_Brief.docx`. Свериться с ним перед созданием/импортом артов, UI, VFX.
- Разработка ведётся вайб-кодингом через Claude Code — именно поэтому архитектурные рамки должны быть явными и соблюдаться без постоянных напоминаний со стороны человека.

## 2. Архитектурные принципы (обязательны)

1. **Разделение данных и логики.** Баланс (урон, HP, стоимости, кривые роста) — только в `ScriptableObject`, никогда не хардкодить числа в коде. Если правишь баланс — это правка ассета в инспекторе, не пул-реквест с изменением кода.
2. **Dependency Injection через конструктор/интерфейсы**, не через `FindObjectOfType` или публичные статические ссылки на менеджеры. Зависимости системы должны быть видны в её конструкторе/полях, а не скрыты внутри методов.
3. **Событийная связь между модулями** (Event Bus), а не прямые ссылки между несвязанными системами. Пример: `EnemyHealth` не должен напрямую знать про `MetaCurrencyManager` — он публикует событие `EnemyKilled`, кто угодно на него подписывается.
4. **Одна ответственность на класс.** Если класс одновременно считает урон, обновляет UI и сохраняет прогресс — это сигнал разделить его до начала следующей фичи, не откладывать "на потом".
5. **Чистая логика отдельно от MonoBehaviour.** Расчёт урона, экономика магазина, кривые опыта/прогрессии — обычные C#-классы без наследования от `MonoBehaviour`, принимающие данные и возвращающие результат. `MonoBehaviour` — только тонкий адаптер между Unity-жизненным циклом и этой логикой. Это открывает возможность покрыть баланс unit-тестами без запуска сцены.

## 3. Обязательные паттерны проектирования

| Задача | Паттерн | Где применяется |
|---|---|---|
| Поведение оружия (Melee/Ranged/AoE) | **Strategy** | `IWeaponBehavior`, реализации на тип атаки |
| Состояние забега (Wave/Shop/Results) | **State Machine** | `RunStateMachine` — явные состояния, не булевы флаги |
| Спавн врагов/предметов | **Factory** + **Object Pool** | `EnemySpawner`, `ProjectilePool` |
| Коммуникация между системами | **Observer / Event Bus** | `GameEvents` — статическая шина типизированных событий |
| Постоянные и временные модификаторы статов | **Composite/Decorator**-подобная агрегация | `StatModifier` + `CharacterStats.Recalculate()` |
| Генерация содержимого магазина | **Strategy** для правил пула по волне | `ShopSlotGenerator` |

Не вводить новые паттерны "для красоты" — только если задача реально требует гибкости, которую даёт паттерн. Оверинжиниринг ради портфолио — тоже антипаттерн: код должен быть explainable на собеседовании простым языком ("я выбрал Strategy, потому что типов оружия будет расти, и каждое ветвление if/switch на тип — сигнал, что нужен полиморфизм").

## 4. Структура и нейминг

```
Assets/_Project/Scripts/
  Core/        — EventBus, ObjectPool<T>, утилиты, не завязанные на конкретную игровую систему
  Player/
  Combat/      — Weapon, StatModifier, CharacterStats, урон
  Enemies/
  Spawning/    — EnemySpawner, WaveConfig-логика
  Shop/        — внутриигровой магазин
  Meta/        — сохранения, мета-прогрессия, MetaShop
  UI/
```

- Namespace на каждую папку верхнего уровня (`Game.Combat`, `Game.Enemies` и т.д.) — облегчает чтение кода вне контекста файловой структуры.
- Публичные члены — `PascalCase`. Приватные поля — `camelCase` с `_` в начале (`_moveSpeed`), сериализуемые приватные поля — тоже с `_`, но с `[SerializeField]`.
- Интерфейсы — префикс `I` (`IWeaponBehavior`, `IDamageable`).
- Никаких сокращений в именах ("mgr", "cfg", "tmp") — полное слово всегда читается быстрее, чем расшифровка сокращения.

## 5. Запрещено (антипаттерны)

- `FindObjectOfType`, `GameObject.Find`, `SendMessage` — в runtime-коде. Только явные ссылки или DI.
- `GetComponent` внутри `Update`/`FixedUpdate` — кэшировать в `Awake`.
- Публичные изменяемые статические поля как замена архитектуре (`public static GameManager Instance` с открытым доступом ко всему) — если нужен единый менеджер, ограничивать его ответственность явно, не превращать в god-object.
- Магические числа в коде (`if (hp < 20)`) — только именованные константы или значения из `ScriptableObject`.
- Глубокая иерархия наследования (`Enemy → FlyingEnemy → FastFlyingEnemy → ...`) — предпочитать композицию через интерфейсы/компоненты.
- Пустые `Update()` методы "на будущее" и закомментированный код, оставленный "на всякий случай" — удалять сразу.
- Corutines и `async/await` не смешивать в рамках одной системы без явной причины — выбрать один подход на подсистему и придерживаться его.

## 6. Производительность

- Object pooling — обязателен с первого дня для врагов, снарядов, дроп-предметов, VFX. Ретроактивно внедрять пулинг дорого — закладывается сразу.
- Не создавать аллокации в `Update`/`FixedUpdate` (никаких `new List<>()`, LINQ-цепочек, boxing в горячих путях).
- Для данных, которые часто создаются и живут недолго (например, промежуточные расчёты урона) — предпочитать `struct`, а не `class`.
- Профилировать (Unity Profiler) при превышении ~150-200 одновременных врагов на арене — не гадать, а измерять.

## 7. Definition of Done для фичи

Перед тем как считать фичу завершённой, проверить:
- [ ] Нет хардкода баланса — всё вынесено в ScriptableObject.
- [ ] Нет прямых жёстких связей между несвязанными системами (проверить через EventBus).
- [ ] Нет `FindObjectOfType`/`GetComponent` в хот-пути.
- [ ] Пуллинг применён там, где объекты создаются волнами/часто.
- [ ] Публичный API класса — минимальный, реализация деталей скрыта (`private`/`internal`, где не нужен доступ извне).
- [ ] Код компилируется без warnings.

## 8. Как ИИ должен подходить к задачам в этом проекте

1. Перед реализацией новой игровой системы — свериться с ГДД (раздел с описанием этой системы), не придумывать механику от себя.
2. Если задача неоднозначна на архитектурном уровне (например, куда должна "принадлежать" новая система) — сначала предложить вариант и спросить, а не молча принимать решение и потом объяснять постфактум.
3. Не делать масштабный рефакторинг существующего кода попутно с несвязанной фичей — рефакторинг обсуждается и делается отдельным шагом.
4. Каждое архитектурное решение (выбор паттерна, структура класса) должно быть объяснимо в 2-3 предложениях — если объяснить сложно, вероятно, решение излишне усложнено для задачи.
5. Коммиты — маленькие и по одной логической задаче за раз (conventional commits: `feat:`, `fix:`, `refactor:`, `balance:` для правок ScriptableObject-данных).
